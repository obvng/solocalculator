# SoloCalculator attack review, 15 November 2026

This is a source review, dependency audit and limited request testing, not a penetration-test certificate. Do not run flooding, request-smuggling payloads or brute-force tests against production.

## Findings and changes

- Login had no persistent throttle. It now consumes an atomic database counter before account lookup and password verification. The shared single-owner budget is 20 attempts per 15 minutes, independent of IP and request headers. Database failures deny login. There is no new database migration: this uses a namespaced key in the existing counter table. This deliberately trades resistance to distributed password guessing for the possibility of a temporary sign-in lockout. Blocked requests do not extend the original window.
- Login now rejects file-valued fields and email/password inputs above 254/1,024 characters. Invalid accounts use the same public credential error. This is not a claim of identical timing for all account states.
- Upload counters were scoped to owner plus IP, permitting fresh budgets when the IP changed. The counter is now owner-scoped. The audit IP hash remains separate.
- Autosave parsed unrestricted JSON before sanitizing HTML. It now requires an approved Origin, checks authentication before reading input, bounds the actual streamed body to 1 MiB (including requests without Content-Length), rejects dangerous prototype keys and malformed IDs/versions, and uses validated SEO/title/slug values for writes. Large articles may need a future deliberately raised limit.
- Session lookup now rejects cookies outside the exact format generated by the server, before database work.
- Updated production dependencies after current advisory lookup: Next.js, sanitize-html, Zod and Vercel Blob. Pinned the patched transitive Vercel OIDC package. The package's presence does not mean the application provides an OIDC login endpoint.

## Requested attack coverage

| Attack | Evidence or boundary |
| --- | --- |
| HTTP/2 Rapid Reset | HTTP termination is Vercel's responsibility. No custom HTTP/2 server in this repository. Account firewall settings and edge mitigation are not proved by application tests. |
| Long username, Unicode identity clones | No public signup or username login. Login compares the full lowercased email against the configured owner and the stored row, without truncation or confusable-character folding. New length bounds precede expensive work. |
| Forged SAML / spoofed Microsoft email | No SAML/Microsoft identity callback or email-claim login in this application. |
| GraphQL alias 2FA brute force / OTP replay | No GraphQL endpoint or OTP-based 2FA feature. Absence of 2FA is not itself a second-factor protection. Passkeys or managed MFA would be a separate change. |
| Regex denial of service | No user-supplied regular expression compilation found. Editor requests are now bounded before sanitization. This review does not prove every dependency regex safe. |
| JWT public-key algorithm confusion | No JWT session verification. Sessions are 32 random bytes, opaque, SHA-256-hashed in the database, and expire server-side. |
| Request smuggling | No custom proxy/parser to patch here. Vercel and framework protocol handling remain upstream boundaries. No destructive production probes were used. |
| Header cache poisoning | Metadata uses the configured site URL. Limited public GET checks with forged X-Forwarded-Host/X-Original-URL did not echo the supplied host. Admin responses are private/no-store. Relevant framework updates included. This is not an exhaustive cache-key audit. |
| Rate-limit header spoofing | Login and upload budgets are independent of forwarded IP headers. Database counters work across application instances. |
| RLS bypass through a view | Application uses server-side Postgres access, not browser-facing Supabase/RLS authentication. No SQL views or RLS policies found in repository migrations. Actual production roles, grants and externally-created views still need a database privilege audit. |
| Math.random / timing token guessing | Session tokens use node:crypto randomBytes(32); uploads use randomUUID. No Math.random authentication tokens found. Database token lookup is not a character-by-character secret comparison. |
| Padding oracle cookies | Session cookies contain opaque tokens, not CBC-encrypted payloads. Secure in production, HttpOnly and SameSite Strict. A stolen valid session remains usable until expiry/logout. |
| Prototype pollution into code execution | No eval/new Function or user-controlled template compiler found in application code. Bounded editor JSON rejects prototype-related keys; relevant dependencies updated. This is not a proof that arbitrary JSON everywhere can safely be merged. |
| Server template injection | React rendering plus allowlisted article HTML sanitization. Article text is not compiled as server code. |
| XML external entities | No XML upload/parser route. Image processing accepts only detected JPEG/PNG/WebP and re-encodes pixels. Static XML sitemap/verification files do not parse submitted XML. |
| WebSocket hijacking | No application WebSocket server or upgrade handler. |

## Remaining operational checks

The patched production dependency audit returned zero known advisories. The all-dependencies audit still lists moderate advisories in development tooling (Drizzle's older loader/esbuild chain and lint glob dependencies). These tools are not exposed as production web endpoints; do not expose local development or migration tooling publicly. The test runner was upgraded to remove its critical advisories.

Review Vercel firewall and account MFA; review Neon roles/grants/network access; rotate any owner password previously shared in chat. These are not established by passing source tests. Keep dependency checks in the release process. No website can honestly be certified free from hacking.

Vercel documents its [Rapid Reset mitigation](https://vercel.com/changelog/strengthening-vercels-infrastructure-against-http-2-rapid-reset-attacks) and [automatic DDoS protection](https://vercel.com/docs/vercel-firewall/ddos-mitigation). Next.js documents [Server Action origin checks](https://nextjs.org/docs/app/api-reference/config/next-config-js/serverActions); explicit checks are needed separately for custom mutation Route Handlers such as autosave.
